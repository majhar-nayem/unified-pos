# ADR-012: Three orthogonal order statuses

- Status: **Accepted**
- Decision area: order lifecycle modelling
- Related: [01 §7.1](../01-system-architecture.md), [02-database-design.md](../02-database-design.md), [03 §5 F4](../03-implementation-plan.md), [05 §4.4](../05-competitive-review-and-plan-critique.md)

## Context

An order has a commercial lifecycle, a preparation/fulfilment lifecycle and a payment lifecycle that advance independently: a restaurant order is open and in preparation while partly paid; a retail order is completed, paid and later partially refunded. Odoo folds these into one `state` enum because its ERP owns accounting and stock (docs/05 §4.4); this platform integrates with external accounting and stays decoupled.

## Decision

Orders carry three status fields:

- `status`: draft → open → completed; open → suspended → open; open/draft → cancelled; completed → voided (authorised only).
- `fulfillment_status`: unfulfilled, in_preparation, partially_ready, ready, fulfilled; derived from lines and kitchen tickets.
- `payment_status`: unpaid, partially_paid, paid, partially_refunded, refunded; derived from captured intents and refunds, never set directly.

A retail sale, a dine-in order and a return are one aggregate (`Order` with `kind`); the check is the billable unit. The only backward transition on `status` that is not a void is `completed → open` for an offline card payment that was declined after forwarding (`orders.reopened_reason`, event `reopened_offline_decline`; ADR-019).

## Alternatives considered

1. **Single composite status enum.** Rejected: combinatorial states (open-and-partially-paid-and-in-kitchen), every new feature multiplies values and transitions.
2. **Separate order types per vertical.** Rejected: two engines for pricing, payment and reporting.

## Consequences

- Positive: each lifecycle has a small state machine that can be tested exhaustively; reports read the field they need.
- Negative: invariants across fields (cannot be `completed` with `payment_status = unpaid` unless tender policy allows) need explicit checks and tests.
- Security: because `payment_status` is derived, an actor cannot mark an order paid by editing status; a gap is that `status = voided` is the fraud-sensitive transition and is gated by `orders.void` plus approval ([threat model](../security/threat-model.md), "refund/void fraud").
