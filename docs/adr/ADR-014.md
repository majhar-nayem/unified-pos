# ADR-014: REST + OpenAPI public API; no GraphQL initially

- Status: **Accepted**
- Decision area: public API style
- Related: [01 §9](../01-system-architecture.md), [03 §7 item 13, §9](../03-implementation-plan.md), [ADR-001](ADR-001.md)

## Context

The same API serves first-party clients and, later, integrators (accounting, ecommerce, delivery, marketplace apps). Integrators need predictable idempotency, pagination, versioning and sandboxing. Security tests need a machine-readable contract (the cross-tenant harness is generated from OpenAPI).

## Decision

REST under `/v1`, OpenAPI 3.1 generated from code (NestJS + zod; served at `GET /v1/openapi.json` with `x-scope`, `x-permission`, `x-public`, `x-operator`, `x-idempotent` extensions). OAuth 2.0 client credentials with scopes (`orders:read`, `inventory:write`), `Idempotency-Key` on all POSTs, cursor pagination, `If-Match` ETags for optimistic concurrency, per-client rate limits, sandbox tenants. Outbound webhooks are HMAC-SHA256 over `timestamp.body` with a 5-minute tolerance, retry with backoff for 24 h, delivery log and replay. No GraphQL or gRPC for the public surface until a concrete need appears.

## Alternatives considered

1. **GraphQL.** Rejected initially: per-field authorization and query cost control are hard to get right with RLS plus scope rules; caching and idempotent mutations are less natural.
2. **gRPC.** Rejected for public use: browser and integrator friction; may be used internally if modules are extracted.

## Consequences

- Positive: contract-driven tests (cross-tenant harness covers every route automatically); easy for integrators.
- Negative: chatty clients for complex reads; mitigated by sync feed for devices and read-model endpoints for dashboards.
- Security: public API is its own trust boundary in the [threat model](../security/threat-model.md); per-client limits from `api_clients.rate_limit_per_minute` are not yet enforced (f1 release note) and are tracked as a gap against F10.
