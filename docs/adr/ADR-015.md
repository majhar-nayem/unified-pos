# ADR-015: OpenTelemetry; Grafana stack (or Datadog if budget allows)

- Status: **Accepted**
- Decision area: observability
- Related: [01 §13](../01-system-architecture.md), [03 §5 F10, §10](../03-implementation-plan.md), [ADR-016](ADR-016.md)

## Context

Diagnosing a failed sale requires following one correlation id across POS, Hub, API, worker, provider call and webhook. Operations need SLO burn alerts and payment-specific alarms (uncertain count, reconciliation exceptions, audit-chain failure, cross-tenant attempt).

## Decision

Instrument with OpenTelemetry in `api`, `worker`, Store Hub and POS (sampled); `correlation_id` from the originating client command flows through events, webhooks and provider calls. Metrics: RED per endpoint, queue lag per stream, outbox backlog, sync lag per device, terminal transaction durations, payment `uncertain` count (pages), RLS context-missing counter (must be zero), device offline counts. Logs: structured JSON, PII-redacted at source. Backend: Grafana/Tempo/Loki/Mimir self-run or managed, with Datadog as the paid alternative; the choice does not change instrumentation (`packages/observability`, owned by S-INFRA).

## Alternatives considered

1. **Vendor-specific agents.** Rejected: lock-in and duplicated instrumentation.
2. **Logs only.** Rejected: no latency or lag visibility across hops.

## Consequences

- Positive: portable telemetry; SLO objectives in architecture §12.1 become measurable.
- Negative: sampling decisions must keep payment and security traces at 100 %; PII redaction at source is a standing review item.
- Security: logs and traces must not contain tokens, enrollment codes, PINs or masked card data beyond last four; the PCI column-name scanner and log-redaction tests belong in CI (plan §9; [threat model](../security/threat-model.md), information disclosure rows).
