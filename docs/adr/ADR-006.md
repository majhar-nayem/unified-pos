# ADR-006: Transactional outbox → Redis Streams; JetStream/Kafka later

- Status: **Accepted**; outbox relay and `processed_events` skeleton implemented in F1
- Decision area: asynchronous messaging
- Related: [01 §1, §9](../01-system-architecture.md), [03 §5 F1](../03-implementation-plan.md), [ADR-001](ADR-001.md), [ADR-013](ADR-013.md)

## Context

Read models, loyalty, inventory consumption from recipes, notifications, webhooks and connectors all react to business events. An event must never be lost between the database commit and publication, and consumers must tolerate duplicates. Throughput at pilot scale is modest (load profile 200 orders/s, plan F10).

## Decision

Events are appended to `outbox_events` **inside the business transaction**. A worker relay claims rows (60 s lease, `SECURITY DEFINER` function so it can cross tenants under RLS), publishes them to a Redis Stream (`pos:events`, consumer groups per consumer), and marks `published_at`. After 10 failed attempts an event goes to a dead-letter stream (`pos:events:dead`) with an alert. Consumers record `processed_events(consumer, event_id)` and are idempotent. Every event carries `tenant_id`, `location_id`, aggregate id and version, `occurred_at`, `causation_id` and `correlation_id`. When fan-out or throughput justifies it, the relay target changes to NATS JetStream or Kafka; the outbox contract and event catalog do not.

## Alternatives considered

1. **Direct publish after commit.** Rejected: a crash between commit and publish loses events (violates the "no acknowledged transaction lost" hard invariant for derived effects such as reconciliation).
2. **CDC only (Debezium).** Rejected for v1: more infrastructure; retained as a fallback for the analytics tier (architecture §10).
3. **Start on Kafka.** Rejected: operational weight without evidence of need.

## Consequences

- Positive: at-least-once delivery with idempotent consumers; same code path locally and in production.
- Negative: relay lag adds latency to read models (shown as freshness); Redis Streams offers weaker retention and replay than Kafka; Redis loss needs the relay to re-publish from the outbox (it can, because the outbox is the source).
- Security: the outbox is a trusted internal channel; webhook delivery is built on it with HMAC signing (architecture §9). The relay's cross-tenant `SECURITY DEFINER` functions are in the privilege-escalation review set of the [threat model](../security/threat-model.md).
