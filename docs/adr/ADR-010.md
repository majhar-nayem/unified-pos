# ADR-010: Payment orchestration with intent/attempt; semi-integrated terminals; zero PAN; terminal modes ranked LAN/SDK first, cloud second; offline declared per mode

- Status: **Accepted, amended 18 Oct 2026** after provider documentation review (docs/05 §3, G1–G3)
- Decision area: payments model and PCI scope
- Related: [01 §7.3, §7.4, §8.3, §11](../01-system-architecture.md), [05 §3](../05-competitive-review-and-plan-critique.md), [payments/capability-matrix.md](../payments/capability-matrix.md), [ADR-019](ADR-019.md), [ADR-020](ADR-020.md), [ADR-013](ADR-013.md)

## Context

Payments are the highest-risk module: duplicate charge, lost acknowledged transaction and false "paid" status are hard invariants. Providers differ in capability (offline, tips, pre-auth, unreferenced refunds, least-cost routing) and in where their terminal API can run. PCI DSS scope must stay minimal; the platform is not a card-data processor.

## Decision

1. **Orchestration layer.** `PaymentIntent` → `PaymentAttempt` state machines with append-only `payment_events` as audit of record; `payment_intents.status` is a projection. `uncertain` is first-class: after a timeout the platform queries the provider (`getStatus`, `lastTransactionResult`) before any retry; a retry is a new intent only after the earlier one is terminal. Idempotency key `(tenant, device, client_intent_id)`, using provider idempotency where offered.
2. **Provider adapter interface** (`PaymentProviderAdapter`, `TerminalAdapter`) with `capabilities()` declared per account **and per connection mode**.
3. **Semi-integrated certified terminals; zero PAN.** The platform never receives PAN, CVV or track data; only tokens, masked data and the terminal's printable receipt block.
4. **Terminal modes ranked** for stores that need offline card: LAN/local terminal API (Adyen local, Tyro iClient) and native SDK (Stripe Terminal mobile/smart-reader) first; cloud terminal API second (no offline card in Adyen cloud or Stripe server-driven). Offline capability is a property of the mode, never of the provider.
5. **UI honesty.** The UI never promises offline card acceptance; the terminal decides.

## Alternatives considered

1. **Single-provider embed (Square-style).** Rejected: vendor lock-in and no economics leverage in Australia (eftpos least-cost routing).
2. **Direct card capture with a tokenisation vault.** Rejected: raises PCI scope to SAQ D-class obligations (see [PCI responsibility matrix](../security/threat-model.md#pci-dss-responsibility-matrix)).
3. **Cloud terminal APIs as the primary mode** (the original text). Superseded by the amendment: provider documentation shows no offline acceptance in those modes.

## Consequences

- Positive: invariants testable at the state-machine level; providers swappable; honest capability claims.
- Negative: terminal adapters run at the store, not only in the cloud, which led to ADR-019; certification effort per provider (Tyro mandatory before production).
- Open validation: capability matrix is populated from vendor docs and still **proposed** until Sprint 0 sandbox tests confirm it ([capability matrix](../payments/capability-matrix.md)).
- Security: card-present integration modes determine PCI responsibility; the matrix is in the threat model document. QSA review before GA; no SAQ level is claimed until then.
