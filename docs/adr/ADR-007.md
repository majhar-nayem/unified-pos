# ADR-007: Drizzle ORM with hand-written SQL migrations

- Status: **Accepted** (Prisma viable if the team prefers; migration semantics are the deciding factor)
- Decision area: data access and migrations
- Related: [01 §14](../01-system-architecture.md), [02-database-design.md](../02-database-design.md), [03 §4 Schema bootstrap](../03-implementation-plan.md), [ADR-002](ADR-002.md)

## Context

The schema relies on features ORMs generate poorly: RLS policies, composite tenant foreign keys, closure-table triggers, partial indexes, exclusion constraints (reservations), append-only triggers, `SECURITY DEFINER` functions and one-transaction `SET LOCAL` context. Migrations must be expand-only so code rollback never needs schema rollback (plan §10).

## Decision

Authoritative schema is SQL: `db/schema*.sql` bootstrap plus numbered hand-written migrations reviewed as SQL (`packages/db/migrations`). Drizzle provides typed table mirrors and query building. A diff-check (`pnpm --filter @pos/db schema:check`, also run against Testcontainers in CI) compares every mirrored table, column, type, nullability and default to `information_schema`; drift fails CI. Drizzle's own migration generator is not used. Raw SQL is used where Drizzle cannot express the construct, always through the tenant-scoped handle.

## Alternatives considered

1. **Prisma.** Viable: better ecosystem; rejected as default because its migration model fights RLS, triggers and `SET LOCAL`, and `migrate dev` semantics assume the ORM owns the schema.
2. **TypeORM / MikroORM.** Rejected: weaker typing and migration story, larger runtime surface.
3. **Query builder only (Kysely) or raw SQL.** Considered; Drizzle chosen for schema mirrors that the diff-check can verify.

## Consequences

- Positive: DBAs and reviewers read the real DDL; RLS and triggers are first-class; the diff-check proves mirrors match.
- Negative: two descriptions of every table to keep in step; mirrors currently cover only tables F1 touches, so tables absent from the mirror are not reported (f1 release note).
- Risk R10 (team unfamiliarity): Prisma fallback documented.
- Security: migrations run under a superuser/BYPASSRLS role that must never be used by the running services; CI and infra must keep that role out of runtime configuration ([threat model](../security/threat-model.md), privilege escalation).
