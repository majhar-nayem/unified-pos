# ADR-002: Shared-schema PostgreSQL with RLS; per-tenant cluster option for enterprise

- Status: **Accepted**; implemented and tested in F1 ([docs/releases/f1.md](../releases/f1.md))
- Decision area: tenancy and data isolation
- Related: [01 §1, §6.2](../01-system-architecture.md), [02-database-design.md](../02-database-design.md), [ADR-003](ADR-003.md), [threat model: cross-tenant IDOR](../security/threat-model.md)

## Context

The product is multi-tenant SaaS with an enterprise hierarchy (tenant → org unit → location → register). Isolation failures are the highest-impact class of defect (cross-tenant data access is a P1, architecture §11). Tenant counts will range from single-store merchants to enterprise groups; enterprise customers may demand dedicated infrastructure and residency (architecture R9).

## Decision

One PostgreSQL (Aurora, multi-AZ) database with shared tables carrying `tenant_id` on every row. Defence in depth, in this order (architecture §6.2):

1. RLS policy `tenant_id = current_setting('app.tenant_id')::uuid` on every tenant table, `FORCE ROW LEVEL SECURITY`, application role is not the table owner, composite foreign keys include `tenant_id`.
2. Repositories are built from a `TenantScopedDb` handle that cannot be constructed without a resolved tenant (`runInTenantTransaction`: `BEGIN` → `SET LOCAL app.tenant_id` → work → outbox/audit → `COMMIT`).
3. `AuthorizationService.can()` is called in application services, not controllers.
4. Out-of-scope object ids return 404; an OpenAPI-driven cross-tenant harness exercises every route with a foreign tenant token.

Tenant → cluster routing is kept possible so an enterprise tenant can be moved to a dedicated cluster without code changes.

## Alternatives considered

1. **Schema-per-tenant.** Rejected: migration fan-out across thousands of schemas, poor connection-pool reuse, no stronger isolation than RLS for a bug in the application role.
2. **Database-per-tenant.** Rejected as the default for cost and operations; retained as the enterprise option.
3. **Application-level filtering only.** Rejected: a single missing `WHERE` becomes a breach.

## Consequences

- Positive: isolation enforced below the application; cheap small tenants; one migration path.
- Negative: RLS policy evaluation cost per row (risk R4; benchmark with 10k tenants in F10); SECURITY DEFINER functions are needed for legitimate cross-tenant jobs (outbox relay, purge, provisioning), and the migration role must be superuser/BYPASSRLS (asserted in `migrate()`), so those functions and that role are high-value targets (see threat model, privilege escalation).
- Verified in F1: a deliberately buggy repository is blocked by RLS (`rls-buggy-repository.integration.test.ts`); cross-tenant harness 146 cases.
- Gap tracked: RLS context-missing counter must be zero and page on non-zero (architecture §13); wiring belongs to S-INFRA / F10.
