# ADR-001: Modular monolith on NestJS; extract payments and reporting first when justified

- Status: **Accepted** (architecture proposal v1; recorded 2026-10-18)
- Decision area: system shape
- Related: [01-system-architecture.md §1, §4, §5](../01-system-architecture.md), [03-implementation-plan.md §1, §2](../03-implementation-plan.md), [ADR-006](ADR-006.md), [ADR-019](ADR-019.md)

## Context

The platform covers 19 bounded contexts (identity, tenancy, catalog, pricing, inventory, orders, payments, kitchen and others, architecture §5) for a small team (plan §3) that has to ship a retail and restaurant pilot in about 14 weeks. Money-moving writes must be atomic: an order line, its tax rows, its inventory movement, its outbox event and its audit row commit together (architecture §5.1). Several concerns have different operational profiles: payments need separate secrets and a narrower database role (PCI scope containment), reporting is read-heavy and tolerates lag.

## Decision

Build one NestJS/TypeScript codebase organised as 19 modules, each with a public application-service interface and owned tables (schema prefix in Postgres). Deploy it as process roles from the same image: `api` (requests, sync endpoints, WebSocket), `worker` (outbox relay, consumers, jobs) and a `payments` deployable (same codebase, separate ECS task, separate secrets and DB role). Modules talk in-process through their public interfaces and through domain events; cross-module table access is forbidden.

Payments and reporting are the designated first extractions. A module is extracted only when one of these holds: independent scaling is measured and needed, a compliance boundary requires it, or a team boundary exists. Until then the boundary is enforced by lint (`eslint-plugin-boundaries`) and an architecture test on Drizzle schema ownership.

## Alternatives considered

1. **Microservices from day one.** Rejected: distributed transactions across orders, payments and inventory would replace one database transaction with sagas before there is any scale evidence. Operational cost (service mesh, per-service pipelines) does not fit the team.
2. **Serverless functions per endpoint.** Rejected: cold starts hurt checkout latency SLOs (p95 < 500 ms online, architecture §12.1), connection pooling to Postgres with RLS context (`SET LOCAL`) is awkward, and the long-running Store Hub and worker roles do not map to functions.
3. **Plain monolith without enforced boundaries.** Rejected: tight coupling is exactly what the competitive review found in Odoo (docs/05 §4.1); boundary lint is cheap insurance.

## Consequences

- Positive: single transaction boundary where correctness needs it; fast iteration; one deployable artefact family; extraction path already marked.
- Negative: a shared runtime means a defect in one module can affect others; mitigated by separate process roles and by the `payments` role having its own task.
- Obligation: the module-boundary lint is in place from Sprint 0; the Drizzle table-ownership architecture test is still open (f1 release note, "Deferred or partial") and must land before more streams add modules.
- Security link: the separate `payments` deployable and DB role are a control in the [threat model](../security/threat-model.md) (refund fraud, webhook forgery, PCI scope).
