# ADR-009: Command-log sync protocol

- Status: **Accepted**; CRDT libraries to be re-evaluated for catalog replicas only
- Decision area: offline synchronisation
- Related: [01 §3, §8](../01-system-architecture.md), [03 §6 M1](../03-implementation-plan.md), [ADR-003](ADR-003.md), [ADR-011](ADR-011.md), [ADR-013](ADR-013.md)

## Context

Stores must keep trading with the internet down, for hours or days. Business facts (sales, payments, stock movements) are naturally append-only; configuration is authored centrally. Row-level replication would force conflict resolution onto domain data that should never conflict, and would bypass server-side authorization, pricing and validation.

## Decision

Devices (and the Store Hub) keep an append-only **command log** in SQLCipher-encrypted SQLite (`commands(client_command_id ULID, type, payload, hlc, created_at, status, server_result)`), plus read-only replicas of catalog and configuration and local projections built by the same `domain-core` reducers the server uses. Protocol:

- Upload `POST /v1/sync/batches`: ordered commands; each processed in its own transaction through the normal application service; result per command `applied | duplicate | rejected{code, detail}`.
- Download `GET /v1/sync/feed?streams=…&cursor=…`: ordered change records from `change_feed`; snapshot endpoint for bootstrap; WebSocket carries hints only, pull is the truth.
- Idempotency on `client_command_id`; per-device ordering preserved; cross-device ordering by hybrid logical clock, server stamps `recorded_at`.
- Conflicts: facts are append-only (no conflict), configuration is server-wins, the one true conflict is concurrent edits to a shared open check with the Hub down (profile C), resolved by Hub authority plus append-merge plus a manager `sync_conflicts` queue. Rejected commands (for example a void now above a cashier's limit) go to a manager queue; the sale stands.
- Business date is computed from the location's time zone and the client `occurred_at`.

## Alternatives considered

1. **CRDT row replication (ElectricSQL, PowerSync).** Rejected for transactional data: re-implements authorization and pricing outside application services; revisit for catalog replicas only.
2. **Last-write-wins row sync.** Rejected: loses facts.
3. **Peer-to-peer device mesh.** Rejected, see [ADR-011](ADR-011.md).

## Consequences

- Positive: small protocol surface; replay after crash harmless; business rules stay in one place.
- Negative: server re-execution means any rule that depends on time or configuration can reject an old command (surfaced, not hidden); the command log is a security-relevant surface: forged or replayed commands must be authenticated per device and re-authorised server-side ([threat model](../security/threat-model.md), "forged commands", "offline tampering").
- Delivery: server endpoints and client in M1 (4 weeks) with chaos tests defined first; `packages/sync-protocol` owned by S-F6a.
