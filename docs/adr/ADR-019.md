# ADR-019: Payments Edge: terminal adapters and the offline store-and-forward queue run on the store network

- Status: **Accepted 18 Oct 2026**; spike R11 in Sprint 0 and Wave 2 confirms host placement per profile
- Decision area: where payment terminal code executes
- Related: [01 §4, §4.1, §7.4, §8.3, §15 R11](../01-system-architecture.md), [05 §3, §6.2, G1/G2](../05-competitive-review-and-plan-critique.md), [03 §4 Payments Edge spike, §6 M11, §13 decision 8](../03-implementation-plan.md), [capability matrix](../payments/capability-matrix.md), [ADR-010](ADR-010.md), [ADR-011](ADR-011.md)

## Context

Provider documentation (October 2026) shows offline card acceptance exists only where the integration runs on the store side: Adyen local Terminal API (cloud mode "not very useful"), Stripe mobile/smart-reader SDKs (JavaScript SDK and server-driven modes unsupported), Tyro iClient over LAN (offline behaviour undocumented). A cloud-hosted `payments` deployable cannot drive those terminals, and a webview-only POS cannot use native SDKs. Offline payments also need caps, expiry windows and a forward-outcome lifecycle that the cloud cannot enforce while disconnected.

## Decision

Introduce a **Payments Edge** component:

- Runs the terminal adapters that must live on the store network (Adyen local, Stripe Terminal SDK, Tyro iClient) and owns the offline store-and-forward queue, per-device count and sum caps, and expiry.
- Hosted as a **Tauri native plugin on the register** (profile B, default proposal for single-register stores) or as a **Store Hub module** (profile C, from M8b). Whether profile B stores may use a mandatory small Hub appliance instead is open decision 8.
- Reports every attempt and outcome to the cloud through the same command log (ADR-009); the cloud `payments` deployable keeps webhooks, settlement import, reconciliation, card-not-present flows and forward-outcome tracking.
- Offline lifecycle: `payment_intents.offline = true`, `forward_outcome = pending` and `offline_expires_at` from the provider window → on reconnect the Edge forwards and records `forwarded_at` → `approved`, `declined`, `expired` or `rescue_in_progress`. Decline or expiry reopens the check (`orders.reopened_reason`, `reopened_offline_decline`), writes a `reconciliation_exceptions` row (`offline_declined`, `offline_expired`) and queues the order for a manager.
- Caps are enforced at the Edge from `devices.health` counters (`offline_payment_count`, `offline_payment_sum_minor`) and proven nightly against `offline_device_seq`.
- The Edge never sees PAN; the terminal remains the card-data boundary.

## Alternatives considered

1. **Cloud-only terminal APIs.** Rejected: no offline card per Adyen and Stripe documentation.
2. **Stripe JS SDK in the webview.** Rejected: no offline mode.
3. **Adapters in the POS webview only.** Rejected for Adyen and Stripe (no native/TLS handling, no Hub reuse); remains the intended model for Tyro iClient (browser JS over LAN), subject to the spike.

## Consequences

- Positive: honest offline card where providers allow it; one lifecycle for all providers; same code path on register and Hub.
- Negative: payment code now ships in client binaries (update/rollback discipline, per-provider certification of the shipped build); the Edge is a new attack surface: a tampered register could attempt to forge outcomes or caps ([threat model](../security/threat-model.md)); LAN TLS certificate handling for Adyen terminals; support for networks (Adyen does not support site network issues, see [supported devices](../operations/supported-devices.md)).
- Risk: offline card depends on LAN integration and provider certification (plan §12; Tyro mandatory, Adyen store-and-forward enabled by Adyen Support); honest UI copy "the terminal may accept card payments offline up to your limit".
