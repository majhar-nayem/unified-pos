# ADR-018: Promotion rules as a validated JSON DSL evaluated by domain-core

- Status: **Accepted**; DSL v1 delivered by S-F3 (percent_off, amount_off, fixed_price, bogo, multibuy, threshold)
- Decision area: promotion engine
- Related: [01 §7.2](../01-system-architecture.md), [03 §5 F3, §6 M5, §7 item 4](../03-implementation-plan.md), [ADR-005](ADR-005.md)

## Context

Merchants configure promotions (buy-one-get-one, meal deals, thresholds, schedules, customer groups). The same rules must evaluate identically on the POS offline and on the server, be previewable in the admin console, be explainable on receipts and in audit, and be safe to author by tenant staff. Odoo's loyalty is 23 modules of screen overrides (docs/05 §6.1), which confirms that a central engine is cleaner.

## Decision

Promotions are data: a JSON DSL validated with zod at write time and evaluated by `domain-core` (ADR-005). Evaluation order: filter by scope, schedule and eligibility → sort by `(priority asc, created_at asc)` → apply respecting stacking groups and exclusions → record a `PromotionApplication` per rule with exact lines and amounts. A full ordered trace is returned for receipts, audit and tests. The DSL is closed (no scripting). Limits on rule complexity and a "minimum margin" control (Phase 3) bound abuse. Golden files cover 150+ cases at F3.

## Alternatives considered

1. **Code plugins per promotion.** Rejected: arbitrary code in the POS core and unreviewable tenant logic.
2. **Rules engine product (Drools-style).** Rejected: heavy runtime, hard to run on devices, poor determinism guarantees.

## Consequences

- Positive: preview equals runtime; offline parity; auditable trace; no code execution risk.
- Negative: DSL expressiveness grows only through releases; the `rules` jsonb has no explicit DSL version column today (only the row `version`), so a DSL version marker inside `rules` is an open item for S-F3.
- Security: promotion editing is a privileged action (price-affecting, dual approval option for bulk changes) and promotions are an abuse vector for discount fraud; see [threat model](../security/threat-model.md), "discount abuse".
