# ADR-011: Optional Store Hub for profile C

- Status: **Accepted**; delivered in two steps, M8a (kitchen tickets and printers) then M8b (shared open checks)
- Decision area: store-local topology
- Related: [01 §3, §4, §8.2, §12.2](../01-system-architecture.md), [03 §6 M8a/M8b, §7 item 14](../03-implementation-plan.md), [05 G7](../05-competitive-review-and-plan-critique.md), [operations/supported-devices.md §8](../operations/supported-devices.md), [ADR-009](ADR-009.md), [ADR-019](ADR-019.md)

## Context

Full-service restaurants, multi-register stores and QSR with KDS need shared live state (open checks, table map, kitchen tickets, printers) when the internet is down. Device-autonomous mode (profile B) cannot show one register's open tables on another. Competitors split: Toast uses a hardwired device as a LAN hub for KDS only (UPnP multicast, one subnet, router restarts break printing until the ISP returns); Oracle Simphony runs CAPS, KDS controller and print controller on site with backup instances (docs/05 §2, G7).

## Decision

An optional **Store Hub** (Node + SQLite, mDNS `_unifiedpos._tcp`) runs on the store LAN, as a dedicated small appliance or as the "primary register in hub mode" (packaging is open decision 4). Rules:

- A device never talks to another device; it talks to the Hub if present, else to Cloud (one-to-one protocol).
- Cloud remains system of record; the Hub is system of record for **live store state only**, for that location, only while operating under profile C. Hub ↔ Cloud uses the same command protocol as a device (ADR-009), authenticated by mTLS or signed requests.
- Sequencing: M8a Hub owns kitchen tickets and printers only (checks stay device-owned, as Toast does); M8b adds authoritative open checks and the Payments Edge module.
- Hardening taken from the competitive review: static-address fallback beside mDNS, one-subnet preflight at enrollment, router guidance, and a Phase 3 failover (secondary hub or primary-register takeover, mirroring Simphony's backup CAPS/KDS controller).
- Loss of the Hub: devices fall back to Cloud, else device-autonomous with read-only view of others' checks; rebuild = re-enroll and resync (architecture §8.4).

## Alternatives considered

1. **Peer-to-peer device mesh.** Rejected: N² connections, split-brain without an authority, hard to reason about per-device protocol and audit.
2. **Cloud-only KDS.** Rejected: fails the restaurant offline promise.
3. **Hub for everything from day one.** Rejected: risk R2; staged M8a/M8b.

## Consequences

- Positive: restaurant offline promise; failure drills as acceptance (internet cut for 4 h, router restart, hub failure).
- Negative: LAN software is a new attack surface and support burden (hub impersonation on LAN, rogue mDNS responders); a single-subnet requirement narrows supported networks.
- Security: devices must authenticate the Hub and the Hub must authenticate devices (pinned Hub certificate delivered at enrollment, device-key signed requests); see [threat model](../security/threat-model.md), "hub impersonation on LAN".
