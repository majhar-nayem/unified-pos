### Search benchmark (100 000 variants, informational)

HTTP end to end through the full guard/interceptor pipeline, one connection, Testcontainers `postgres:16`, developer laptop.

| Run                                      | Barcode lookup p50 / p95 / p99 (ms) | Fuzzy search p50 / p95 / p99 (ms) | Fuzzy top-3 hit rate |
| ---------------------------------------- | ----------------------------------- | --------------------------------- | -------------------- |
| First version (plain query as `app_rw`)  | 1.3 / 2.1 / 3.1                     | 219 / 330 / 468                   | 100 %                |
| Final (`fn_search_items`), quiet machine | 2.3 / 3.6 / 5.1                     | 13 / 17.6 / 30                    | 100 %                |
| Final, machine loaded by other streams   | 7.5 / 21.7 / 30                     | 26 / 55 / 92                      | 100 %                |

**Finding worth keeping:** under `FORCE ROW LEVEL SECURITY` the planner does not push non-leakproof operators (`tsvector @@`,
`pg_trgm <%`) into index conditions, so the straightforward query run as the application role was a **sequential scan**
(200 ms at 100k rows, ~2 s expected at 1M) while the same query as the table owner used Bitmap Index Scans and took 10 ms.
Equality lookups (barcode, SKU, id) are leakproof and unaffected. The fix is `catalog.fn_search_items` (migration 0003 §E), a
tenant-pinned `SECURITY DEFINER` function that filters explicitly by `platform.current_tenant()`. Any later module that needs
`@@` or trigram search over a tenant table will hit the same wall and should follow the same pattern.

## Decisions worth knowing

1. **Tenant-wide catalog, location-scoped operations.** Items, categories, modifiers, suppliers and tax data are tenant-level (`x-scope: tenant`); reads need `catalog.view` anywhere, writes need the permission at tenant scope (a location-scoped manager gets 404, as in F1). Two things are genuinely location-scoped and use the hierarchy: the **86 list** (`/v1/locations/{id}/availability`, `catalog.availability.manage` at that location) and **menu assignments** (`catalog.menu.manage` is checked at the assignment's own scope, so a store manager may assign menus at their store but not at a sibling or the tenant). Menu resolution requires `catalog.view` at the location.
2. **Keyset pagination is always in id (creation) order.** The first version ordered categories by path with an `id > cursor` predicate and silently skipped/duplicated rows (caught by the pagination test). Lists now order by id only; categories carry `path` so a client builds the tree itself. Import jobs are newest first (`id <`).
3. **Seed inserts are plain inserts.** They skip authorization and the per-row audit/outbox entries so provisioning still writes exactly one audit row and one event (the F1 acceptance test asserts that). Services expose `insertRaw`/`insertConversionRaw` for that and the audited `create` wraps them.
4. **The tax resolver returns one rule, not a stack.** Ranking is priority, then specificity (class, then region), then latest `valid_from`, then id. `compound` is stored and returned but not applied; stacking several rules (GST plus a levy) is a pricing-engine decision for F3. With no matching rule the effective rate is `0` and `inclusive = true`, so totals never grow unexpectedly.
5. **Menu resolution reads live rows.** Only `published` menus resolve; `valid_from` inclusive, `valid_to` exclusive; weekdays are ISO (1 = Monday); a window whose `from` is later than `to` spans midnight and its early-morning part belongs to the previous day's entry in `days`; `from == to` means all day. `menus.version` bumps on publish and on header edits, **not** on section or item edits: devices refresh on `menu.published` and `catalog.item.changed`.
6. **Search uses the `simple` text-search configuration** (product names are multilingual and brand-like, stemming hurts) and `pg_trgm` word similarity (`<%`, floor 0.5) for typos, ranked by the better of the two signals. `catalog.fn_search_items` is `SECURITY DEFINER` but pinned to the session tenant and returns nothing when none is set (tested, including that a second tenant never appears).
7. **Import is create-only and all-or-nothing.** A row error rejects the file and writes nothing, but the job and its report are kept (HTTP 201 with `status: rejected`). Prices and costs are read in major units with the tenant currency's exponent (JPY has none) and stored as bigint minor units. SKUs and barcodes that already exist are errors, not updates.

### CSV import format

UTF-8, RFC 4180, header row required, up to 5 MB. Columns (unknown columns are errors): `item_ref, item_name, item_kind, category_code, tax_class_code, sold_by, unit, sku, variant_name, option_values, price, cost, barcode, barcode_kind, pack_quantity, track_inventory`. Rows with the same `item_ref` (or `item_name`) are variants of one item; a repeated `sku` adds another barcode to that variant. `option_values` is `size=L;colour=red`, `price`/`cost` are major units. Report columns: `line, column, code, message` (21 error codes in `CATALOG_IMPORT_ERROR_CODES`; the report holds the first 1 000 errors, the summary the true count).

## Known limitations

- Benchmarks stop at 100k variants; the 1M target is untested. The barcode index is the canonical `UNIQUE (tenant_id, code)` and should scale, search at 1M needs a re-run.
- The tax resolver applies a single rule; compound/stacked taxes, customer exemptions and `kind`-based combination are not modelled (F3).
- The AU seed is unconditional: a tenant provisioned for another country gets AU GST rows it must replace (tax rules are editable data).
- Import: no GTIN check-digit validation, no update/upsert of existing SKUs, runs synchronously inside the request and emits one audit and one outbox event per created row, so very large files are slow; an async job runner is planned.
- Menu edits below the header do not bump `menus.version` (see decision 5); the resolved menu does not apply the 86 list or resolve prices (F3 and the POS combine them).
- Recipes are read-only and `modifier_recipe_effects` has no API (M10). Item `unit_of_measure` is not validated against `units_of_measure` on item create/update.
- Search: `simple` configuration, no accent folding (`unaccent` is not installed), ranking is a blend of `ts_rank_cd` and word similarity, not tuned on real catalogs.
- `item_availability` has no version column, so concurrent 86-list edits are last-write-wins.

## Security considerations

- Every route goes through the F1 pipeline: authentication, `ScopeGuard`, contract validation (422 with issue trees), `AuthorizationService` in the services, then RLS. Out-of-scope and foreign ids answer 404, never 403, and never leak ids (158 generated cases).
- Referenced ids in bodies (parent category, tax class, variants, supplier, scope of an assignment) are looked up inside the tenant transaction, so a foreign id is a 404 and the composite tenant FKs are the last line.
- `catalog.fn_search_items` is the one new `SECURITY DEFINER` function: pinned to `platform.current_tenant()`, empty result without a tenant, `search_path` fixed, `PUBLIC` revoked, tested against cross-tenant leakage. The migration role must be a superuser or hold `BYPASSRLS` (already asserted by `migrate()`).
- Import reports escape cells starting with `= + - @` (spreadsheet formula injection) and never echo more than the offending value; the upload is capped at 5 MB.
- No PCI scope: prices and costs only, no card data.
