## Architectural decisions

1. **One aggregate, pure reducers.** `packages/domain-core/src/orders` has no I/O: every command is `(state, input, ctx) → { state, events }` with the clock, actor, id source and `PricingPort` injected. The API loads the aggregate under `SELECT … FOR UPDATE`, runs the reducer, and writes back only what changed. Devices can run the same reducers offline.
2. **Totals are recomputed on every mutation through the pricing port** and satisfy the table CHECK (`total = subtotal − discount + (tax if exclusive) + charges + tip + rounding`) at order and check level; a helper restates that CHECK and the property tests assert it after every random command.
3. **Concurrency.** The order row lock serialises commands; `save` still guards on the loaded `version`. Line adds commute, so `If-Match` is optional there: without it 50 parallel adds all succeed (versions 2…51), with it exactly one of N wins and the rest get 412. Every other edit requires `If-Match` (428/412). The `Idempotency-Key` header doubles as `client_command_id` on `order_events`.
4. **Status model.** `create` makes a `draft`; `place` (draft → open) assigns the canonical number and emits `order.placed`; a fully paid order completes through `markPaid`. Suspend is only from `open`, exactly as §7.1 lists it, so parking a retail cart means placing it first. Draft → cancelled and open (nothing paid) → cancelled and completed → voided all use `POST /void`; discarding a draft needs only `orders.create`.
5. **Returns carry negative amounts** (positive quantity, negative gross), so summing `total_minor` over orders gives net sales. A return line refunds `round(net × returned_after / qty) − round(net × returned_before / qty)`, so partial returns add up to exactly what was paid. The source order is never edited except `returned_quantity`, line status `returned`, and refund state when the return completes.
6. **Permission or approval** (`ApprovalGate`): the caller holds the permission within limits, or presents an approval whose payload hash matches `{ permission, attributes?, orderId, orderLineId?, … }`. Out of scope is always 404. The approval is **consumed after the request has been validated by a dry run and before the order transaction opens**, because consumption commits on its own connection and nesting it inside the order transaction can starve the pool. The cost: if the order transaction then fails (for example an `If-Match` conflict), the approval is already spent and must be requested again.
7. **Receipts freeze at issue.** One model is built under the order lock, then HTML, PDF, text, ESC/POS and the model JSON are stored; later renders read the stored files (410 `RECEIPT_CONTENT_GONE` if one is missing). Text and ESC/POS can be laid out again at another paper width from the stored model. Asking again for a sale, refund or void already issued for the same check is recorded as a `reprint` row (`-R<n>` number, copy count, audit action, order event) and needs `orders.receipt.reprint`.
8. **Shared lines.** A shared item becomes fractional portions on separate checks, each with a fixed gross allocated by largest remainder, so portions add up to the original exactly; line discounts become fixed amounts allocated the same way; a new check created by a split gets its own copy of any percent service charge.
9. **Business date** follows the location time zone and day boundary at placement; an offline order keeps the date of its device clock (`clientCreatedAt`). `order_number_sequences` is one atomic upsert, gap-free inside the placing transaction.

## APIs introduced (24 operations, all under `/v1`, all declare a permission and a scope)

`POST /orders`, `GET /orders`, `GET /orders/{orderId}`, `GET …/events`, `PATCH /orders/{orderId}`, `POST …/lines`, `PATCH|DELETE …/lines/{lineId}`, `POST …/lines/{lineId}/void`, `POST …/discounts`, `DELETE …/discounts/{discountId}`, `POST …/charges`, `DELETE …/charges/{chargeId}`, `POST …/suspend`, `POST …/resume`, `POST …/place`, `POST …/void`, `POST …/checks/split` (modes `lines`, `seats`, `share`), `POST …/checks/merge`, `POST …/returns` (return or exchange), `POST|GET …/receipts`, `GET …/receipts/{receiptId}`, `GET …/receipts/{receiptId}/render?format=html|pdf|escpos|text&columns=`.

Every mutating POST requires `Idempotency-Key`; PATCH/DELETE and every state command except line add require `If-Match`. Error codes are stable rule codes (`ORDER_NOT_EDITABLE`, `EMPTY_ORDER`, `RETURN_QUANTITY_EXCEEDED`, `LIMIT_EXCEEDED`, `APPROVAL_PAYLOAD_MISMATCH`, …). Outbox events: `order.placed`, `order.completed`, `order.voided` (also for a placed order that is cancelled), `order.returned`.

## Known limitations and defects to hand to the integration lead

1. **`apps/api/src/identity.integration.test.ts` now fails** at "system roles are seeded…": it asserts the exact permissions of a cloned `cashier` role. New expectation: `['approvals.request', 'orders.create', 'orders.discount.apply', 'orders.view']`.
2. **`apps/api/src/cross-tenant.integration.test.ts` fails** on unknown fixtures (128 problems, mostly catalog and payments). For orders, add `orderId`, `checkId`, `otherCheckId`, `lineId`, `discountId`, `chargeId`, `receiptId` to the registry; `seedOrderFixtures({ server, token, locationId })` from `modules/orders/public/testing` creates them through the API. This stream's own harness test already covers its 24 operations.
3. **S-F5 declared a different `OrderPort`** (`apps/api/src/modules/payments/ports/order.port.ts`: payments pushes absolute aggregates through `applyPaymentTotals`, `applyCashRounding`, `reopenForOfflineFailure`, `getCheck`). The port this stream provides (`orders.OrderPort` in domain-core, implemented by `OrderPortService`) is incremental: `applyPayment` per `paymentRef`, `markPaid`, `applyRefund`, `reopenOffline`, `getTotals`. They need an adapter in the integration slice: `applyPaymentTotals` → set check paid/refunded from the aggregates and derive `payment_status`; `applyCashRounding` → `applyPayment`'s `roundingMinor` path; `reopenForOfflineFailure` → `reopenOffline`. Decide in Wave 2 which side owns the rule that all checks paid completes the order.
4. **Schema gaps worked around** (no column exists, SQL not editable under §15.2): a fixed line gross (shared portions, returned lines) lives in `order_lines.metadata._grossOverrideMinor`; a rule-based charge keeps `{ percent, taxable }` in `order_charges.distribution`; a discount's `amount_minor` doubles as "what its percent resolved to". A later migration should add `order_lines.gross_override_minor`, `order_charges.percent` and `order_charges.taxable`.
5. `order.returned` is not in the shared `EVENT_CATALOG`; `ORDER_EVENT_NAMES` in `contracts/orders.ts` lists all four events. Add the name to the catalog.
6. Approvals spent before a failing order transaction are not restored (decision 6). A shift supervisor cannot file approval requests in the shipped roles (`approvals.request` is a cashier permission), so refund approvals are requested by the cashier at the register.
7. **PDF is not HTML-to-PDF.** It is the fixed-width layout set in Courier, written without a library; that needs no headless browser and is deterministic. Real HTML-to-PDF needs a renderer decision.
8. The receipt title is "Tax Invoice" whenever the legal entity has a tax registration number, the receipt is a sale and tax is non-zero; the AU $82.50 threshold and other jurisdictions are not modelled. Tax on charges is merged into the single taxed rate when unambiguous, otherwise shown as "Tax on charges" (charges store no rate).
9. Business-day state is not enforced (an order can be placed on a closed day); F9 owns open/close. A register is checked to belong to the order's location; `employee_id` is passed through and relies on the composite FK.
10. A receipt is written to the object store inside the database transaction; a rollback leaves an orphaned object (harmless garbage, never referenced).
11. `orders-world.ts` carries one `eslint-disable boundaries/dependencies` for importing the app-shell test bootstrap, with a comment: integration tests compose the whole application.

## Security considerations

- Every statement names `tenant_id`; RLS is the second layer. A foreign tenant, or a principal scoped to another location, gets 404 for every operation (harness, plus explicit tests for the order, events, receipts and every command).
- Authorization runs in the service against the order's location (`orders.view`, `orders.create`, `orders.discount.apply`, `orders.void`, `orders.line.void`, `orders.refund.create`, `orders.price.override`, `orders.receipt.reprint`), never in the controller; limits (`orders.discount.max_percent`, `orders.refund.max_minor`, `orders.price_override.allowed_categories`) are the existing ABAC keys. An amount discount is judged by the percent it amounts to.
- Approvals are bound to the exact action by payload hash and are single use; the approver must hold the permission within their own limit (the supervisor-versus-manager cases are tested).
- `order_events` is append-only (trigger; update and delete fail even for the superuser); every command writes an audit entry (with `approval_id` and `on_behalf_of` when an approval was used) in the same transaction as the change.
- Receipt HTML escapes every dynamic string and makes no external request; object keys are validated and cannot leave the store root. No card data is handled here.

## Deployment

No migration and no new environment variable is required to run. Optional: `OBJECT_STORE_LOCAL_DIR` (receipt files; default is the OS temp directory, so set it, or the S3 adapter, anywhere that is not a developer machine). The outbox relay already carries the four order events. System roles are global and re-seeded from `@pos/auth` on every API start (`SeedService`), so existing tenants receive the new permissions with the next deploy; signed-in sessions may keep their previous permission set until they refresh or log in again (not verified).
